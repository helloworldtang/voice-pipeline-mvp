- 新测试 `tests/test_trace.py`（10 条：恒等式 / flame graph / 跨窗口边界 / attrs 往返 / 树生命周期）。

## 关键实测（Apple M5，n=6/组，real-serial + qwen-flash + conservative 判停）
| 配置 | 口径B p50 | tts.first_chunk | llm.ttft | 首句成 | 上行竞争 | 残差 |
|---|---|---|---|---|---|---|
| melo（默认） | 1966 | 1526（78%） | 222 | 108 | 50（3%） | 0 |
| kokoro | 2759 | 2365（86%） | 228 | 128 | 52（2%） | 0 |
| 云流式 dashscope | 1029 | 600（58%） | 279 | 111 | 41（4%） | 0 |

- 判停 p50 ≈ 506~514ms（在口径B 之外、体感之内）。`asr.finalize` 0.2ms、`tx.first_audio` 0.08ms。
- **结论：纯本机下限 ~1.9s 级；混合部署（云流式 TTS）~1.0s 级；300ms 差 3 倍，是时序模型问题不是调参问题。**
- P0 行动：默认 TTS 换云流式（省 ~930ms，抵得上其余所有优化之和）。

## 踩到并修掉的三条（都有回归测试）
1. `Tracer.start(**attrs)` 会把名为 `attrs` 的关键字整包吞成 `{"attrs": {...}}`
   → 改显式 `attrs: Mapping | None` 参数。
2. `TurnMetrics.reset_turn()` 会把 span 树清掉 → 判停前的 60 个 uplink.frame 全丢，
   trace 里 0 个上行帧，"上行零开销"是假象。改为**树生命周期归 Session**：
   本轮第一帧开 `turn` 根、`turn.end` 闭根、下一轮第一帧 reset（安全性：上一轮账在
   TurnEnd 那一刻已落盘，收到与落账之间无 await）。
3. `exclusive_times` 边界未夹紧窗口 → "整段在窗口前结束"的 span 塞进 `< lo` 的边界，
   Σ自有 比口径B 多 54ms（**高估**比低估更难发现）。

## 口径提醒
- 分格表必须用**自有时间**（flame graph），不能用 sibling 原始时长相加：
  `llm.request`（2406ms）时间上嵌套 `tts.synth`（1918ms），相加 4324ms > 口径B 2406ms。
- 恒等式自检：`Σ自有 == 覆盖并集`，探针每轮打印，>1ms 报警。

# 2026-10-17 晚 深拆（第二层 span：provider 内部时刻）

## 做了什么
- provider 侧记 phase 时刻（perf_counter 原值，`last_phases` 约定属性），调度器用
  `Tracer.record_perf`（经 `SessionClock.ms_at` 时钟换算）补记子 span：
  - `QwenLlm.astream`：`start/headers/first_line/first_content` → `llm.headers` + `llm.prefill`
  - `DashScopeTts`：SDK 回调里记 `open/first_data/complete` + `construct/submit`
    → `tts.connect`（submit→on_open）+ `tts.first_byte`（on_open→first_data）
  - `metrics/trace.py` 新增 `record_perf` / `phases_of` / `phase_span`（缺端点返回 None，宁空不填 0）
- `pipelined._fallback` 补了原本缺失的 llm span（未命中轮的 LLM 时间原先全落进"真·未归因"）。
- `probe_trace.py` 加 `--llm-model`；`probe_tts_firstchunk.py` 加建连/首字节拆分；
  `report_turns.py` 加 `--spans`（线上账单也能看分格）。

## 关键实测（dashscope + qwen-flash，n=6，口径B p50=1029ms）
| 段 | p50 | 占比 |
|---|---|---|
| tts.first_byte（服务端合成） | 332 | 32% |
| **tts.connect（建连+认证，每句都付）** | **257** | **25%** |
| llm.headers（发包→响应头，网关+RTT） | 231 | 22% |
| llm.first_sentence | 120 | 12% |
| tts.first_chunk 自有（SDK 队列） | 31 | 3% |
| 残差 | 0 | 0% |

- **建连那 257ms 是过去整块归给"TTS 首片"的隐藏成本**：`DashScopeTts.synth()` 每句新建
  `SpeechSynthesizer`（`_close_ws_after_use` 默认 True）。隔离探针 n=12：首片 604ms =
  建连 259 + 服务端 338；TCP 握手只要 40ms。**SDK 自带 `SpeechSynthesizerObjectPool`**
  （借出即预连、`close_ws_after_use=False`），实测借出后首片 340~375ms。
  ⇒ **P0.5 = TTS 连接预热，−230~260ms，当前账面最大可省一笔**。也可"判停即预连"
  （建连不依赖文本，可与 351ms 的 LLM 段并行）。
- **LLM 换模型救不了**：A/B（n=5，同链路只换模型）：qwen-flash ttft 284ms 最快；
  qwen3.7-flash 11342ms（先吐 2811 字思考链，直连 SSE 复核）、qwen3.8-flash 2803ms（95 字）、
  deepseek-v4.1-flash 4059ms、step-3.7-flash 直接 400。新"flash"全是推理型，
  而 QwenLlm 只转发 content → 表现为"久不出声"（刻意的可观测失败）。
- **llm.prefill 只有 0.1ms**：网关把首 token 前的等待并进响应头；旁证：同主机
  `GET /models` ttfb 就要 208ms（含 80ms TLS）。
- **Jev（TypeSafe 决策模型）顶替不了 LLM**：只输出是/否/分类/分值，不生成自然语言。
  EOU 判停理论对口但延迟同量级（70~500ms + 跨洋 RTT vs 500ms 静音窗）省不出东西；
  唯一 plausible 槽是 barge-in 意图分类（二期）。无 key 未实测。

## 新踩的坑
- `record_perf` 必须走时钟换算：provider 在 SDK 线程里只有 perf 原值，各自找原点相减会漂移。
- 测试断言别用 sleep 精度（macOS 上 30ms sleep 实测 38ms），要测**换算精确相等**。
- phase 值必须是真实 perf_counter：拿 1.0/2.0 当绝对时刻会被 ms_at 换算成负数，
  而 `Span.dur_ms` 把负数当"未闭合"返回 -1（MISSING）——假数据会伪装成缺失。

# 2026-10-17 夜 P0.5 落地：TTS 连接预热（自建池）

## 做了什么
- `providers/tts/dashscope_tts.py` 重写：自建连接池（不采用 SDK 的
  `SpeechSynthesizerObjectPool`——cosyvoice-v1 硬编码、replenish 不受控）。
  沿用 SDK 改名私有方法：`__connect`（预连 WS）/`__reset`/`__update_params`
  （换回调 + **新 task_id**，同一连接上第二个任务必须换 id）/`__is_connected`。
  关键：`close_ws_after_use=False` 才可复用（SDK 默认 True = 每句付建连）。
- 预热时机三处均**非阻塞**：建会话（`session._prewarm_tts`）/ 判停
  （`serial.on_end_of_utterance` 首行）/ 投机开跑（`pipelined._start_speculation`，
  用户还在说就热上——建连不依赖文本，天然可与 LLM 并行）。LLM headers ~230ms 即窗口。
- 池纪律：只在事件循环里触碰池状态（无锁）；温连接已死且**未出片** → 冷路径重试一次；
  出过片绝不重试；barge-in 放弃消费 → `_recycle` 轮询 `callback.finished` 等合成真正
  结束再回收（防 InvalidTask）；`_drop` 触发背景补位。
- 能力探测降级：取不到四个私有方法或缺 `audio_format` → 整条预热路径关闭退回冷路径
  （宁可不快，不可半温不热地炸）。
- **修了一个真 bug**：`call()` 抛 ConnectionError 时无回调投哨兵 → `queue.get()` 永久挂起
  （旧探针「偶发卡死」根因）。`fail_sentinel` done callback 仅在异常结束时投 None。
- 新测试 `tests/test_tts_pool.py`（13 例）+ `tests/test_prewarm_wiring.py`（3 例）；
  探针 `probe_trace.py --no-prewarm` / `probe_tts_firstchunk.py --no-prewarm` 对照臂；
  账单 span 增 `a.warm` 属性（0/1，`report_turns.py --spans` 可见）。

|---|---|---|---|---|

## 新踩的坑
- SDK `call()` 是**异步提交**：提交后立即返回，音频在路上——结束信号只能是
  `on_complete`/`on_error`，不能拿 call() 返回当结束（测试假件必须照这个语义造）。
- 假件「complete_event 未清理即炸」用来验证 `_recycle` 真的在等合成结束，不是走过场。
- 测试断言 `warm_acquires` 时注意失败的那次借用也计数；`_drop` 的背景补位会让
  `made` 多 1；预热失败永远不会满池 → `pool_stats` 加 `prewarming` 字段供 settle 判据。
- 沙箱 TMPDIR 限制导致 `tmp_path` 用例 PermissionError，`--basetemp=.pytest_tmp` 绕过
  （环境问题非代码问题，跑完删除）。
