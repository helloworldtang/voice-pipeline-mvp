## 重要纠错：激进门控压的是口径B，不是口径A（推翻 09-20 我的诊断）
用户追问「激进门控与目标一致还是冲突」→ 复核发现自己上一轮判断错了：
- **错在把「激进」当成一件事**。实为两种：A型=用户还在说就出声（抢答，压口径A）；B型=用户说完后不等完整静音窗、用语义判停确认即播（**压口径B**）。
- 文档 §2.1 前提①描述的正是 B 型；§11 却定性为「它压的是口径A」——**两处本就打架**，我上一轮只采信了后者。
- 铁证：waterfall 里 `eou` 与 `utterance_end` 是两个独立打点 → 口径B = first_audio_out − utterance_end **包含判停等待**。等完整静音窗 500-700ms ⇒ 口径B ≥ 500-700ms，**300ms 数学上不可达**。故激进门控是口径B 达标的**必要前提**（§2.1 那句「是 300ms 级数字的前提」才是对的）。
- 代价不是「激进」本身，是**判错**：安全性来源从「时间冗余」换成「语义置信度」。所以激进门控与 EOU 语义判停是**配套的两端**，不是二选一——这正解释了为何 EOU 该在 M2 主线。
- **指标缺口**：文档只写了 turn-detector 中文 TPR 99.3%，但 TPR 高只说明「该停时肯停」；抢话风险看的是**过早判停率 premature_eou_rate**（判停后 300ms 内用户又开口的比例）。缺它则激进门控代价无法度量/验收。
- 建议改法（待用户拍板）：门控分三档 conservative / semantic（M2 后默认）/ aggressive（仅实验）；删 §11 错判句；补 premature_eou_rate 进 §3 指标。
- **不影响 M0/M1 实现**（都先按 conservative 写），故可推迟到 M2 实测再定默认值，但文档错判句必须现在改。

## EOU 判停调研（用户质疑「十多年前的老问题不可能没成熟办法」→ 确实有，且我们漏了一路）
- **谱系**（已写入技术方案 §12.1）：1970s 会话分析 TRP → 静音阈值 hangover(200-500ms) → **2003 SRI 韵律判停（不需 ASR，Ferrer/Shriberg/Stolcke）** → 2008 CMU Raux&Eskenazi 动态阈值(延迟 −22~24%) / FSTTM(−40%) → 2022 KTH VAP(预测未来2秒双方语音活动) → 2024-25 LiveKit v0.4 文本语义 → 2025-09 Pipecat Smart Turn v3(纯音频含韵律, 8MB/CPU 12ms) → 2026 LiveKit v1 双分支融合 + eot-bench。
- **核心结论**：答案从来不是"只靠静音时长"，而是**韵律(怎么说的) + 语义(说了什么)** 两路融合。本仓原方案只有语义一路，**漏了声学/韵律**——这是最大的可补缺口，成本极低（Smart Turn v3 8MB / CPU 12ms，开源权重+数据+训练脚本）。
- **纯文本语义有硬天花板**（LiveKit 官方）：停顿瞬间转写相同，"pizza…" vs "pizza… and garlic bread" 只能靠韵律区分。
- **中文是难点**：Smart Turn v3 中文 acc 88.57 / **FP 4.76(抢话)** / FN 6.67，23 语言中倒数第 6；LiveKit v0.4 中文 TPR 99.3 / TNR 86.6。口径不同不可横比 → **必须自建中文集实测**。
- **验收形态改为错误率–延迟权衡曲线**（eot-bench 形态），不再报单点数字。参考：LiveKit v1 在 300ms 预算下错误率 9.9%，600ms 下 4.5%，≤10% 错误需 295ms。
- **视觉/唇形（评论区白小龙）归类澄清**：视觉主解**说话人归属/抗干扰**（谁在说），不是"说完没有"；纯音频链路里非主流（2025 IWSDS 综述仍称未来方向）→ 不进一期。声纹/多麦波束/说话人分离同属归属层。
- 已写入：技术方案 §12（含待决策点 D1–D5：补 L2 韵律 / EOU 选型 / 门控三档默认值 / 验收曲线 / 中文测试集）+ 背景与基线 §4.7 + §3.2 归类澄清 + §4.3 第 5 条。D1–D5 均不阻塞 M0/M1。

### 血泪：pump 与连接关闭的竞态（曾让 test_ws.py 整体挂死）
- **症状**：`test_ws.py` 无报错挂死，只能被 120s SIGTERM 杀掉。
- **真因**：`run_turn` 把本轮 TurnItem 全投进 outbox 后即结束，但 `pump` 是独立协程未必发完；接收循环 `await turn_task` 返回后发 `session.closed` + `break`，`finally` 的 `pump_task.cancel()` 可能在 `turn.end` 发出前掐掉 pump → 客户端永远等不到 `turn.end`。**`await websocket.send_text(...)` 只排队、不保证 pump 已排空**（两个协程谁先被调度不确定）。
- **修法**：`SessionEnd` 分支 `await turn_task` 后显式 **`await session.outbox.join()`**，pump 每发一项调 `task_done()`。
- **定位手法**（可复用）：① `pytest --timeout=15 --timeout-method=thread` 定位挂在哪条用例的哪一行；② 用**守护线程** `faulthandler.dump_traceback(file=f, all_threads=True)` 写文件（faulthandler 的 `dump_traceback_later` 定时器在本沙箱不触发，且 Bash 工具超时会杀掉整个进程组导致后续 `cat` 跑不到——要用子进程 `subprocess.run(timeout=)` 兜住并读 `TimeoutExpired.stderr`）；③ 关键分支打 `print(..., flush=True)` 看真实收发序列。
- **护栏**（含反向自测）：`pyproject.toml` 加 `pytest timeout = 30`，把死锁从「挂死」变成明确失败。反向自测已做：摘掉 `join()` → 31s 报 Timeout 且堆栈可见；还原 → 71 绿。
- **诚实边界（已写进技术方案 §14.5）**：L1 纯能量判定会被自激误触发，一期靠**入耳式耳机**物理隔离，软件 AEC 列二期；`barge_in_latency_ms` **不含客户端播放缓冲残留的停播耗时**，真实端到端尾音待真机实测。
