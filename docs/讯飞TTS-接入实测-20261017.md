# 讯飞在线语音合成（v2 流式）接入实测：供应商侧 137ms，链路里 216~411ms

> 2026-10-17 · 结论先行：**讯飞做到了服务端首包 p50 137ms（≤150ms 门槛），
> 但初接进链路只省下 39ms**（619→580），因为建连与 GIL 争用把它吃掉了。
> **补上「判停即预建连」之后，口径B p50 = 306ms（n=11，min 244 / p90 352）**——
> 比基线 619ms 快 313ms（−51%），第一次摸到 300ms 线。

## 一、探针结论（供应商侧，可信）

`scripts/probe_vendor_tts.py` + 独立脚本，n=8，同一台机器、同一网络：

| 量 | p50 | 范围 |
|---|---|---|
| WS 握手（TLS + 101） | **38ms** | 34~66 |
| 服务端首个音频包 | **137ms** | 132~146 |
| 合计 | **175ms** | |

对照组：DashScope CosyVoice 在流水线内 `tts.connect 43~50 + tts.first_byte 344~421` ≈ **387~470ms**。
单看这一格，讯飞**快 ~210ms**，是达标（≤150ms）的。

### 三条踩过的坑（都已写进实现）

1. **`aue=raw` 只在 16k/8k 生效**：`auf=audio/L16;rate=24000` 会返回
   `code=0 message=success`，但 `data.audio` 长度为 **0**——静默失败，不报错。
   16k 正常（24064B），8k 正常。所以要 16k 收、`soxr.ResampleStream` 流式重采样到 24k。
   按块独立重采样会在每 200ms 边界爆音，必须用带状态的流式重采样器。
2. **连接不能复用**：同一 WS 上发第二个任务（`status:2`）会**超时**，服务端一个任务后即收尾。
   所以每条句子各自建连，没有"热连接池"可省——DashScope 那条 840→37ms 的预热红利在这里不存在。
3. **鉴权顺序**：签名是 `host: {host}\ndate: {date}\nGET {path} HTTP/1.1` 的 HMAC-SHA256，
   再 base64 成 `authorization` 查询参数。第一版 401 是截图转写错了一个字符，
   剪贴板文本重写后即通——**凭证不要从截图转写**。

## 二、接进链路后为什么拿不到（两处自身开销）

同一份 provider，三种环境的 `tts.first_chunk`（服务端埋点，`span.tts.first_chunk`）：

| 环境 | tts.first_chunk | 其中建连 | 其中收帧 |
|---|---|---|---|
| 独立进程探针 | **84~103ms** | 37~57 | 46 |
| 链路内 + SimLlm | **216~254ms** | **114~129** | 90~128 |
| 链路内 + MLX | **411ms** | — | — |

两个放大器：

- **建连从 38ms 涨到 114~129ms**：同一个 provider、同一台机器，进到 uvicorn 进程里握手就慢了 3 倍。
  逐条排查排除 DNS/证书后，最像的是事件循环在握手期间被别的协程任务挤占（TLS 握手是分多次回调完成，
  每次回调之间都要排队）。
- **MLX 线程把 GIL 抢走**：`tts.first_chunk` 216 → 411ms，就是换上本地 MLX LLM 的净代价。
  这与之前"微基准 45ms、流水线里 140ms"是同一个根因（见 `docs/本地栈可行性-20261017.md`）。
  云 LLM 不占本地 GIL，所以 DashScope 那条 `tts.connect` 在流水线内一直是 43~50ms 没变过。

**净结果**（同一台机器、同一个 scripted wav、`real-serial`）：

| 组合 | 口径B p50 | 备注 |
|---|---|---|
| mlx + DashScope（基线） | **619ms** | `v0.2.1` 收口值 |
| mlx + 讯飞 | **580ms**（575~602） | n=5，方差反而变小 |
| SimLlm + 讯飞 | 249ms（108~286） | 实验室口径，不代表可交付 |

## 三、首片 60ms 开关（做了，默认关）

`Chunker(first_min_ms=...)`：首片只要求 N ms 音频即可下发。动机是讯飞首包 40~90ms，
等凑满 200ms 才发首片会把省下的时间原样吐回去。
实测在 MLX 组合下**没有收益**（口径B 仍 ~580），因为瓶颈在 `tts.first_chunk` 之前不在分片。
它还会打破"所有分片等长"这条既有约定，而守这条约定的 `tests/test_ws.py` 当前不可改
（凭据判据误拦），所以做成 `VOICE_FIRST_CHUNK_MIN_MS`，**默认 0=关**，门禁 230 passed 不变。

## 四、预建连落地（已做，默认开）

思路：既然讯飞连接不能复用，那就**在判停触发时先把 WS 握上**（`prewarm()`，调度器在 EOU 时已
调用这个钩子），等首句文本到了直接发——握手整段藏进 finalize + LLM 首句的窗口。

实测（同一 provider，`XFYUN_DEBUG=1` 打点）：

| | 改前 | 改后 |
|---|---|---|
| `connect`（链路内） | 114~141ms | **0ms**（命中 11/11 次） |
| `tts.first_chunk` | 216~411ms | **48~55ms**（好窗口）/ 114~138ms（抖） |

净效果（`mlx + 讯飞`，scripted wav，`real-serial`，n=11）：

| 口径B | p50 | p90 | min | max |
|---|---|---|---|---|
| 改前 | 580 | 602 | 575 | 602 |
| **改后** | **306** | 352 | **244** | 371 |

分格（改后，好窗口那一轮）：`finalize 27 + prefill 66~141 + 首句 74~105 + tts 48~55`。

语义细节（都有单测钉住，`tests/test_xfyun_tts.py`）：
- **一次性**：预建连用掉就作废，第二条句子必须重连（讯飞一连接一任务）。
- **TTL 10s**：过期连接丢弃并关闭，防旧签名 401 / 服务端静默断链。
- **失败无害**：预建连失败只在后台记 debug，`synth` 自己重连。
- 开关 `VOICE_XFYUN_PREWARM`，默认 1。

现在最大的不确定项变成**讯飞侧的收帧水平漂移**——它不是逐请求随机，而是**窗口级分层**，
见下节。

## 五、收帧抖动的性质：窗口级分层（100 轮实测）

用 `scripts/probe_xfyun_jitter.py`（只留 provider + 预建连，剥掉 LLM 与链路）在 15 分钟内
连打 5 组 × 20 轮：

| 窗口 | n | p50 | 组内极差 |
|---|---|---|---|
| 20:39 | 20 | 121ms | 33ms |
| 20:44 | 20 | **172ms** | 67ms |
| 20:47 | 20 | **51ms** | 89ms（一个 131ms 离群） |
| 20:51 | 20 | 129ms | 40ms |
| 20:54 | 20 | **48ms** | 15ms |

全部 100 轮：p50 **117ms**，min 42 / max 209。

**这不是"每次请求都可能 47 也可能 245"**，而是：

- **组内极稳**：20 轮挤在一起，极差多在 15~40ms，没有双峰；
- **组间跳档**：20:44 的 172 → 20:47 的 51，三分钟内掉 3.4 倍，然后 20:51 又回到 129；
- 观察到的档位约 **50 / 130 / 170ms**，像是命中了不同的接入节点或不同的排队状态。

所以之前那句"同一时段测到 47 和 245"**说法不准**：47 与 245 分别取自不同条件
（245 那次是独立进程与 MLX 服务同时在跑），本次干净测量把它收敛成"三档窗口漂移"。
对口径B 的影响是**整段平移**：命中 50 档 → 口径B ~250；命中 170 档 → 口径B ~350。

## 五之二、尾部对冲为什么无效（当场否证）

假设是"多开一条连接可能落到快节点"。测法：**同一瞬间并发开两条独立连接**，同一句文本，
看是否出现"一条 50、一条 240"。

| 组 | 连接 A | 连接 B | 差 |
|---|---|---|---|
| 1 | 255 | 244 | 12 |
| 2 | 209 | 241 | 32 |
| 3 | 288 | 245 | 43 |
| 4 | 243 | 281 | 37 |
| 5 | 94 | 94 | **0** |
| 6 | 97 | 95 | 2 |

中位差 22ms，**六组没有一次一快一慢**——同瞬间的两条连接落在同一档。
第 5 组还正好撞上整档切换（243→94），两条一起变。

结论：**档位按时间/账号走，不按连接走**，所以
① "直接用快档"没有旋钮可拧；
② 同厂重发/多发拿不到快档，对冲无效（省下的额度是真金白银）。
对 DashScope 对冲同样不划算：它 p50 344ms，比讯飞最慢档 287ms 还差。

**TTS 这一格到此为止：我们能做到"预建连 + 用当下的档位"，剩下的由对方决定。**

## 六、下一步（按收益排序）

1. ~~EOU 即预建连（估 −110ms）~~ ✅ 已落地，实测 −274ms（580→306）。
2. ~~收帧尾部对冲~~ ❌ **实测否证**（见 §五之二）：档位不是按连接分配，多开连接拿不到快档；
   对 DashScope 对冲也不划算（其 p50 344ms 比讯飞最慢档 287ms 还差）。
3. **TTS 出进程**（估 −190ms，代价大）：把 讯飞 的 WS 处理放到独立进程/线程池，
   规避 MLX 的 GIL 争用。工程量大，且与"单机降级"目标冲突，优先级低于 1。
4. **压 LLM 首句**：改后 prefill 66~141 + 首句 74~105 已是最大一格（~180~245ms），
   比 TTS 的 50ms 重得多。要继续往 200ms 走，得动这里（如更短的首句护栏、更小的模型）。
5. ASR 判停 575ms 仍占体感一半以上，但那是"抢话"风险，不在本方案。

## 七、复现

```bash
# 供应商侧
source ~/.voice-pilot/vendors.env
uv run python scripts/probe_vendor_tts.py --repeat 5

# 链路内（讯飞）
source ~/.voice-pilot/vendors.env
VOICE_PIPELINE_TTS_ENGINE=xfyun VOICE_LLM_ENGINE=mlx XFYUN_DEBUG=1 \
  VOICE_EVENTS_JSONL=/tmp/vp-ac/xf.jsonl ./scripts/dev_server.sh
uv run python scripts/scripted_client.py --wav /tmp/vp-ac/up.wav --repeat 5 --mode real-serial
```

凭证只放 `~/.voice-pilot/vendors.env`（600），代码只读 `XFYUN_TTS_APPID/API_KEY/API_SECRET`，
缺了就**响亮失败**，不静默退本地替身。
