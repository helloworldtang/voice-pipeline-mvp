# 链路追踪：耗时到底花在哪（2026-10-17）

> 回答两个问题：① 按**分布式链路追踪**（TraceID + Span）的口径，`口径B（说完→AI首音）`
> 的每一毫秒归谁；② 下一轮迭代该往哪投。所有数字本机实测（Apple M5），
> n=6/组，`scripts/probe_trace.py` 一条命令复现。
>
> 与 `docs/流程拆解与优化空间.md` 的分工：那份是**格子级结论**（每格多少、能不能并行），
> 这份是**归因方法与新证据**（怎么证明没有藏账、哪些格子过去被算错了）。
> 两份数字冲突时以本文为准——本文的每格都过了恒等式自检。

## 一、为什么 waterfall 打点不够，要上 Trace/Span

`metrics/events.py` 的 TurnMetrics 记的是一串**绝对时刻**，分析靠两个时刻相减。
它在"串行 + 全埋到"时够用，但有三个失效方式，这次全撞上了：

| # | 失效方式 | 本次实测撞到的实例 |
|---|---|---|
| 1 | **混账**：两个时刻之差里夹着没埋的东西 | `utterance_end → llm_first_token` 这一格里夹着 `asr.finalize` 与事件循环调度。埋了 span 才知道 finalize 只有 **0.2ms**（可忽略），但**在埋之前没人能证明它可忽略** |
| 2 | **重叠不可见**：并发区间相减会重复计数 | `llm.request` 与 `tts.synth` 时间上嵌套（serial 在 LLM 循环体内 await 合成）。两条 sibling 时长相加 = 4324ms > 口径B 2406ms，**加总比总数还大** |
| 3 | **漏测不可见**：瀑布表没有"未覆盖"这一格 | 判停前的 60 个上行帧原本被 `reset_turn()` 连树一起清掉，trace 里 0 个 `uplink.frame`——看起来"上行零开销"，其实是**证据被自己抹了** |

所以按分布式追踪的最小模型重写：**区间 + 父子关系 + 属性**，并强制一条会计恒等式当自检：

```
口径B 窗口 = Σ(每毫秒归一个 span 的自有时间) + 未归因残差
```

残差非 0 就说明还有东西没埋到。本次实测残差 **p50 = 0ms**（见 §三），
也就是"没有第三个藏账的地方"这件事第一次有了证据，而不是靠信任。

## 二、实现（四件，全在仓库里）

| 件 | 文件 | 是什么 |
|---|---|---|
| 追踪模型 | `src/voice_pipeline/metrics/trace.py` | `Tracer` / `Span`（区间+父子+属性）+ `decompose` / `union_ms` / `exclusive_times` / `stats` / `parse_spans` |
| 埋点 | `core/scheduler/serial.py`、`core/scheduler/pipelined.py`、`server/session.py`、`server/app.py` | 见下面的 span 清单 |
| 探针 | `scripts/probe_trace.py` | 进程内驱动真链路（真 ASR + 真 LLM + 可选三种 TTS），**判停后继续按 100ms 喂静音帧**（麦克风不关），输出分格表 + span 树 + 逐轮 JSONL |
| 回归 | `tests/test_trace.py`（10 条） | 恒等式、flame graph 归属、跨窗口边界、`attrs` 往返、树生命周期 |

### span 清单（一棵树长这样）

```
turn                       ← 整轮根：本轮第一帧上行 → turn.end（兜住"用户说话期间"）
  ├─ uplink.frame × N       ← 每帧；子：asr.push_audio（线程里的活）、eou.update（循环里的活）；
  │                           被 P1 能量门拦下的帧打 a.gated=1 且无 asr.push_audio 子 span
  └─ turn.caliber_b         ← 口径B 窗口：说完 → 首音（延迟分析的主战场）
       ├─ asr.finalize      ← utterance_end → transcript（过去混在 LLM 账上）
       ├─ llm.request       ← 整段生成（**嵌套**下面两个，且常常跨过窗口右边界）
       │    ├─ llm.ttft     ← 首 token（**= headers + prefill**，2026-10-17 晚深拆）
       │    │    ├─ llm.headers    ← 发包 → 响应头：网络 + 网关
       │    │    └─ llm.prefill    ← 响应头 → 首 content：服务端排队+prefill
       │    └─ llm.first_sentence ← 首 token → 首句末标点
       ├─ tts.synth         ← 合成整句（seq/chars 属性）
       │    └─ tts.first_chunk   ← 合成 → 第一个可播分片（**= connect + first_byte**）
       │         ├─ tts.connect    ← call 提交 → WS on_open：建连+认证（每句都付）
       │         └─ tts.first_byte ← on_open → 首个音频分片：服务端合成
       └─ tx.first_audio    ← outbox 入队 → 真正落网线（transport 那一跳）
```

**为什么 `turn` 与 `turn.caliber_b` 要分两层**：只记口径B 的话，
"用户说话期间链路在干什么"（ASR partial 节奏、EOU 每帧开销、判停前最后几帧）
在账单里是空白；而这一段恰恰解释尾部异常（判停 1.4~2.1s 那几轮）。

### 三条实现纪律（都是这次踩出来的）

1. **`attrs` 用显式参数，不用 `**attrs`**：后者会把叫 `attrs` 的关键字整包吞成
   `{"attrs": {...}}`——埋点看着写了，roundtrip 时键名对不上，取不到值。
2. **`reset_turn()` 不清树**：清树的时机只能是**下一轮第一帧**（上一轮的账在
   TurnEnd 那一刻已落盘，收到与落账之间没有 await，所以安全）。
3. **边界必须夹在窗口内**：`exclusive_times` 的边界若直接用 `min(end, hi)`，
   "整段在窗口前结束"的 span 会塞进一个 `< lo` 的边界，Σ自有 比口径B 多出 54ms——
   错的方向是**高估**，比低估更难发现。有回归测试钉住。
4. **provider 的 phase 时刻必须走时钟换算**（`SessionClock.ms_at` + `Tracer.record_perf`）：
   DashScope SDK 在另一个线程里回调（on_open/on_data），只有 perf_counter 原值；
   两边各自找原点相减会整体漂移，账面上看不出来。换算误差有回归测试钉**精确相等**。

## 三、实测：三种 TTS 引擎的分格（n=6，real-serial，conservative 判停）

上行语音固定「我想问一下明天上海天气怎么样，适合出门吗」（4.0s，kokoro 合成），
判停后持续喂 100ms 静音帧（251~293 帧/轮）。

| 段（自有时间） | melo p50 | kokoro p50 | 云流式 dashscope p50 |
|---|---|---|---|
| **口径B 合计** | **1966ms** | **2759ms** | **1029ms** |
| tts.first_chunk | **1526ms（78%）** | **2365ms（86%）** | **600ms（58%）** |
| llm.ttft | 222ms（11%） | 228ms（8%） | 279ms（27%） |
| llm.first_sentence | 108ms（5%） | 128ms（5%） | 111ms（10%） |
| asr.finalize | 0.2ms | 0.2ms | 0.2ms |
| tx.first_audio | 0.08ms | 0.09ms | 0.07ms |
| 上行帧 CPU（窗口内） | 50ms（3%） | 52ms（2%） | 41ms（4%） |
| **未归因残差** | **0ms** | **0ms** | **0ms** |

> dashscope 那行的 `tts.first_chunk` 600ms 当时还是黑箱；它的内部（建连 257ms +
> 服务端首字节 332ms）见 §四 深拆——**这一格 43% 是建连，与首句字数无关**。

口径B 之外但计入体感：**判停 p50 ≈ 506~514ms**（conservative 档的静音窗）。
`含嵌套` 参考：`llm.request`  Inclusive 2356~2563ms——它跨过窗口右边界继续跑
（LLM 说完整段答案比首音晚得多），`tts.synth` Inclusive 1999~2179ms。

### 三条读数

1. **TTS 首片是唯一的一等公民**：三组配置里都占 58%~86%。
   换掉本地引擎（melo→云流式）一刀 **省 ~930ms**，比"优化其他所有格子加起来"还多。
2. **没有藏账**：残差 0ms，`asr.finalize` 0.2ms、传输跳 0.08ms 都小到可以忽略。
   过去担心的"混账"被量化后可判：**ASR finalize 不是问题，TTS 才是**。
3. **上行不是免费的，但很小**：持续喂帧时，口径B 窗口内被上行吃掉的循环时间
   p50 41~52ms（最差一轮 159ms）。这是本次**新量出来**的一格——
   它是 `ASR 前置 energy gate` 的收益上界；该优化已于当天落地
   （§四 4.5：同时段 A/B 口径B p50 −97/−113ms，比这里预估的 ~40ms 更多）。

## 四、深拆：两个最大格子的内部（2026-10-17 晚，第二层 span）

第一层分格（§三）说「TTS 首片占 58~86%、LLM 首 token 8~27%」，但这两个格子各自还是
黑箱：600ms 里多少是网络、多少是服务端？换模型有没有救？第二层埋点把 provider 内部
时刻也变成 span——`llm.headers`/`llm.prefill`（QwenLlm 在 astream 里记 perf 原值）与
`tts.connect`/`tts.first_byte`（DashScope SDK 回调里记），恒等式仍每轮自检。

### 4.1 云流式配置的口径B 全解剖（dashscope + qwen-flash，n=6，p50）

> ⚠️ **这是 P0.5 之前（每句冷建连）的账**：口径B 1029ms 里有 259ms 是建连。
> 建连移出窗口后的现行账见 **§4.6（775ms）**——本节的格子名称不变，数值已过时。

| 段 | p50 | 占口径B | 是什么 |
|---|---|---|---|
| **口径B 合计** | **1029ms** | 100% | |
| tts.first_byte | 332ms | 32% | WS on_open → 首个音频分片：**服务端合成** |
| tts.connect | 257ms | 25% | call 提交 → on_open：**建连+认证，每句都付** |
| llm.headers | 231ms | 22% | 发包 → 响应头：网络 + 网关 |
| llm.first_sentence | 120ms | 12% | 首 token → 首句末标点 |
| tts.first_chunk（自有） | 31ms | 3% | 首片过 SDK 队列到调度器 |
| asr.finalize / 传输跳 / 上行竞争 | ~1ms | ~0% | |
| **未归因残差** | **0ms** | 0% | 没有第三个藏账的地方 |

三条读数：

1. **过去整块归给「TTS 首片」的 600ms，43% 是建连**。`DashScopeTts.synth()` 每句
   新建 `SpeechSynthesizer`，WS 连接不复用。隔离探针（`probe_tts_firstchunk.py`，
   n=12）同句重复：首片 p50 **604ms = 建连 259ms + 服务端首字节 338ms**；而同主机
   TCP 握手只要 40ms。**SDK 自带 `SpeechSynthesizerObjectPool`**（预建 WS、借出时
   `close_ws_after_use=False`），实测借出后连续调用首片 **340~375ms**，run-task 握手
   从 259ms 降到 0~54ms——这 259ms 是可去的，且是当前账面最大的一笔。
   另一条路同理：**建连不依赖文本**，把它挪到 LLM 之前/之中（与 351ms 的 LLM 段并行）
   也能整段藏掉。
2. **LLM 首 token 284ms 几乎全在网关侧**：`llm.prefill` 只有 0.1ms——网关把首 token
   之前的等待并进了响应头。旁证：同主机静态端点 `GET /models` 的 ttfb 就要 208ms
   （含 80ms TLS，热连接约 130ms）。本地无从优化，除非换离网关更近的部署。
3. **首片与首句字数基本无关**：隔离探针 1 字 688ms vs 25 字 612ms（服务端首字节
   419 vs 351，噪声范围）。压答案长度对云流式无效——与 §六 P3 的结论一致，但这次
   有了内部证据。

### 4.2 换 LLM 模型有没有救：A/B 实测（同链路，n=5，只换模型）

| 模型 | ttft p50 | 首句成 p50 | 口径B p50 | 备注 |
|---|---|---|---|---|
| **qwen-flash（现默认）** | **284ms** | 132ms | 1137ms | 思考链 0 字 |
| qwen3.7-flash | 11342ms | 111ms | 11996ms | 先吐 **2811 字思考链**（直连 SSE 复核） |
| qwen3.8-flash | 2803ms | 250ms | 3828ms | 思考链 95 字 |
| deepseek-v4.1-flash | 4059ms | 98ms | 4479ms | n=2，其余轮次异常 |
| stepfun/step-3.7-flash | — | — | — | 400 Bad Request |

**结论：现默认 qwen-flash 就是全平台最快的**。名字带 flash 的新模型全是推理型
（`reasoning_content` 非空、`content` 迟数秒），而 `QwenLlm` 只转发 `content`——
换推理模型的表现是「久不出声」（刻意的可观测失败，不是把思考念出来）。
「用最近的模型缓解延迟」在这个平台上方向相反。复现：
`uv run python scripts/probe_trace.py --tts dashscope --llm-model <模型> --repeat 5`。

### 4.3 Jev（TypeSafe 决策模型）能不能用：顶替不了 LLM，也救不了判停

Jev 是 2026-09 发布的 **System One 决策模型**：输入「状态 + 问题」，输出**是/否、
分类、分值**等结构化结论（70~500ms，输出不计费），**不生成自然语言**。逐槽对照：

| 槽位 | Jev 能否顶替 | 理由 |
|---|---|---|
| 回复生成 LLM | **不能** | 它写不出「明天上海多云转晴，适合出门」——语音助理要的是自由文本 |
| EOU 语义判停（我们失效的启发式 L3） | 理论对口，实测不推荐 | 判停确是「说完了吗」这种是非题；但 Jev 自身 70~500ms + 跨太平洋 RTT，与 conservative 的 500ms 静音窗同量级，**省不出延迟**；官方明言非英语（含中文）效果不如英语 |
| barge-in 意图分类（文章第二层） | 唯一 plausible 的槽 | 「嗯」vs「等等你说错了」是分类题，且不押关键路径；属二期，且要 key 才能实测 |

**无 key，未实测**（OpenRouter 上的 OpenJEV 需自有账号）。结论先行：**Jev 缓解不了
我们的延迟**——地板是 TTS 首片（连接 + 服务端），不是「模型不够聪明」。

### 4.4 P0.5 落地：连接预热（2026-10-17，当天闭环）

§六 的 P0.5（「建连 259ms 本可藏掉」）已实现并实测。做法不是 SDK 的单例对象池
（它用 cosyvoice-v1 硬编码自建连接、 replenish 不受我们控制），而是在
`DashScopeTts` 里自建小型连接池，语义：

- **预热时机**：建会话 / 判停（serial）/ 投机开跑（pipelined）——都不等建连完，
  LLM 那几个往返（headers ~230ms）就是预热窗口；建连 ~260ms 全部藏在
  「用户还在说/还在想」里，不进口径B。
- **复用协议**：借出时走 SDK 改名私有方法 `__reset()`（清 complete_event）+
  `__update_params(...)`（换回调 + **新 Request/task_id**——同一连接上第二个
  任务必须换 id）——与 SDK 自带对象池同一套路。取不到这些方法（SDK 版本变了）
  或没有 format 回填信息时，**整条预热路径关闭**，退回 2026-10-17 前的冷路径。
- **保活与自愈**：温连接被服务端空闲掐线且**尚未出片** → 冷路径重试一次
  （出过片绝不重试，音频已经出门）；**预热建连失败 → 重试一次**（`WARM_RETRY_DELAY_S=0.15`，
  仍失败才计数并退回冷路径）；消费端提前退出（barge-in）→ 等合成真正
  结束（on_complete/on_error）再回收连接，否则同一合成器会被两个任务同时用
  （InvalidTask）。顺带修掉一个真 bug：`call()` 炸掉时没有任何回调触发哨兵，
  旧代码会永远等在 `queue.get()` 上——2026-10-17 探针里「偶发卡死」的根因。

实测（同机同时段，`probe_trace.py --tts dashscope --repeat 6`，两臂只差预热开关）：

| 臂 | 口径B p50 | 逐轮口径B | tts.connect p50 | 池计数 |
|---|---|---|---|---|
| 预热开（现默认） | **724ms** | 660~777ms（**含第 1 轮**） | **38ms** | warm=6 / cold=0 |
| 预热关（对照） | 700ms | **第 1 轮 1317ms**，2~6 轮 637~785ms | 38ms（max 273） | warm=5 / cold=1 |

- 预热把**每会话第一轮**从 1317ms 压到 777ms（−540ms）；第 2 轮起两臂相同
  （池跨轮复用，不依赖预热）。
- 对照 2026-10-17 早段的归档基线（旧代码，每句冷建连）：口径B p50 1029ms、
  tts.connect 257ms。现在 **724ms / 38ms**，恒等式残差仍为 0。
- 隔离探针（n=8，真 SDK）：预热臂首片 p50 **406ms**（冷启动那次 646ms），
  connect 259→59ms，0 失败；复用协议（reset/update_params/task_id 轮换）
  与并发（2 会话共享单例池，834/810ms，满载拒绝 1013 不变）均验证通过。
- span 级证据：`tts.synth` 的 `warm` 属性（1=热连接）逐句落账，
  预热开=6/6 全 1，预热关=第 1 轮 0、其余 1。

### 4.5 P1 落地：ASR 前置能量门（2026-10-17，当天闭环）

§六 的 P1（「判停后客户端仍在喂帧，静音帧不推 ASR」）已实现并实测。做法：

- **门在哪**：`core/energy_gate.py` 的 `AsrEnergyGate`，接在 `Session.on_audio` 里
  `scheduler.on_audio()`（= ASR）**之前**；EOU 仍收全部帧——静音正是判停的原料，
  门只拦 ASR，不拦判停。
- **门限取 0.01（EOU `ENERGY_THRESHOLD`），不是 barge-in L1 的 0.02**：门的假阴性
  代价是**丢语音**（整段轻声被拦在 ASR 外），比误打断更贵；本仓测试里就有
  RMS≈0.018 的轻声帧，0.02 会把它们整段拦掉。不变式 `gate.threshold <= L1`：
  L1 认定的人声必须能进 ASR，两层不许互相抵消（有单测钉住）。
- **滞后语义**：进静音要慢（连续 3 帧低于阈值才确认），出静音要快（任意一帧
  超阈值立即恢复推流）——句中停顿不误伤。
- **只在 real 模式生效**：SimAsr 的 `text()` 按 push 次数前进，拦静音帧会把确定性
  回放变成非确定性；且 SimAsr.push_audio 没有 ONNX 解码可省。
- span 证据：被拦帧在 `uplink.frame` 上打 `a.gated=1`（不再产生 `asr.push_audio`
  子 span），`report_turns --spans` 可直接数。

**顺带修真 bug 两枚**（都是这轮挖出来的，不是设计时想到的）：

1. **L1 每帧算两次 `is_speech`**：`on_audio` 原实现每帧调两次，`_above` 去抖计数器
   双倍计数——文档写的「3 帧去抖」实际 2 帧就触发。改为每帧算一次复用，恢复文档
   语义（既有测试注释本就按 3 帧写，现有单测钉「恰好第 3 帧」）。
2. **`finalize()` 缺尾部静音上下文，尾字整段丢失**（A/B 首轮挖出）：流式 Paraformer
   的 `input_finished()` 解不出缓冲区尾段——隔离实验 19 字掉到 15 字。门拦掉判停后
   客户端追加的静音帧后，ASR 缺尾部上下文，首轮门开臂转写 **18/19 字**（门关臂 19）。
   修法：`finalize()` 自补 600ms 全零静音再 `input_finished()`（隔离实验 300/600ms
   均完整解出；对已喂静音的路径转写一字不变；成本 ~1ms 名义 / 6ms 实测，在口径B
   窗口内）。契约有零网络单测钉住（`tests/test_asr_finalize_tail.py`：残余部分窗
   先于尾静音进流、`input_finished` 必须发生在静音之后，违约直接炸）。

实测（同机同时段，`probe_trace.py --tts dashscope --repeat 6`，两臂只差能量门开关，
预热两臂都开；**跑了两轮**，第二轮在 finalize 修复后复跑）：

| 轮次 | 臂 | 口径B p50 | 逐轮范围 | 上行/EOU 竞争 p50 | 门拦截帧 p50 | 转写 | 判停 p50 |
|---|---|---|---|---|---|---|---|
| R1（修复前） | 门开 | 720ms | 590~856 | 10ms | 22 帧 | **18 字** | 512.9ms |
| R1 | 门关 | 817ms | 677~927 | 37ms | 0 | 19 字 | 510.1ms |
| R2（修复后） | 门开 | **759ms** | 656~904 | 14ms | 26 帧 | 19 字 | 513.7ms |
| R2 | 门关 | 872ms | 688~1003 | 32ms | 0 | 19 字 | 513.2ms |

- **两轮各自同时段对照，口径B p50 −97 / −113ms**，方向与机理一致；逐轮范围有重叠，
  所以报 p50 不报单轮。R1 的 18 字是精度代价，R2 的 19/19 证明 finalize 补静音已消除。
- span 可直接指认的只有「上行/EOU 竞争」−27 / −18ms；其余是二阶效果——省掉的每帧
  `np.concatenate` + 线程派发让下游调度的抖动整体提前（同轮 `llm.headers`
  220→185 / 269→245ms 同向移动），但这部分**不独占一格，不计独功**。
- **判停不受影响**（设计如此）：`eou_latency_ms` 两臂 513 vs 513ms，
  `premature_eou`/`missed_eou` 全 0——EOU 收全部帧，门只拦 ASR。
- 与 P0.5 后的 724ms（§四 4.4，不同时段）同量级，跨时段绝对值不可比；恒等式残差
  仍 0、`|Σ自有−覆盖|` 仍 0.00ms、池 warm 6/cold 0 两臂一致。

### 4.6 P0.5+P1 之后的口径B 解剖（**775ms**，取代 §4.1 的 1029ms）

> 2026-10-17 晚复测（`probe_trace.py --tts dashscope --repeat 6`，关 filler 臂；
> 开臂见 §三①，两臂口径B 无差）。口径B 从 1029 降到 775，**不是某一格变快了，
> 是建连那一格被移出了窗口**（`tts.connect` 257→50，剩余 50 是复用协议本身）。

| 阶段（span） | p50 | 占 775ms | 是什么 | 可动性 |
|---|---|---|---|---|
| `tts.first_byte` | **344ms** | **44%** | WS 连上 → 服务端首个音频分片 | ❌ 本机地板（见下） |
| `llm.headers`（TTFT） | **249ms** | **32%** | 请求 → 首 token（实测 131~324 抖动） | ⚠️ 同 region / 档位，非单机可解 |
| `llm.first_sentence` | **126ms** | **16%** | 首 token → 首句完整（≈**3.8ms/字**，n=6） | ✅ 短首句（唯一 prompt 可动格） |
| `tts.connect` | 50ms | 6.5% | 复用协议：`__reset` + `__update_params` | △ 私有 API，risk 高 |
| `asr.finalize` | 6ms | 0.8% | 19 字终稿 | ❌ 已到底 |
| `eou.update` + `uplink.frame` | ~10ms | 1.3% | 窗口内上行帧 + EOU 喂帧（门只拦 ASR） | ❌ |
| `tts.first_chunk` | 5ms | 0.6% | 分片封装 | ❌ |
| `tx.first_audio` | 0.02ms | — | outbox → 网线 | ❌ 无排队 |
| **未归因残差** | **0.0ms** | — | 没埋到的时间 | — |

> 分位不可加（各格 p50 之和 790 ≠ 775）；**逐轮**的 Σ自有 与窗口时长严格相等，残差 0.0。

**四条读数**

1. **`tts.first_byte` 344ms 已是本机地板**：建连被 P0.5 移走后首片 604→344；本机 TCP 握手
   只有 40ms（占 12%）——**不是网络，是服务端合成首块**。要动只能换 region/厂商。
2. **`llm.headers`(TTFT) 249ms 是第二大块，也是抖动最大的格子**（131~324）。单机侧无抓手。
3. **`llm.first_sentence` 126ms 是唯一还能靠 prompt 动的格子**（≈3.8ms/字）：首句 27→12 字
   约省 57ms。⚠️ 别和 TTS 首片混——**流式首片对字数不敏感**（§一 #6），短首句省的是
   「TTS 请求晚发出」的那一段。
4. 其余全部 <25ms：**口径B 里已经没有「流程浪费」可挖**，只剩三个外部成本 + 一个 prompt 格。

**两个读图陷阱（最容易误读的地方）**

- `llm.request` 2.2s / `tts.synth` 1.9s **不是** provider 延迟：LLM 生成与 TTS 合成是**串行交错**的
  （调度器在 `async for piece` 里 await 合成），那两根 span 被下游背压拉长，`tts.synth` 时长
  ≈ 音频本身长度。可比的是 `llm.ttft` / `llm.first_sentence` / `tts.first_byte` 三根。
- **判停不在这个窗口里**（口径B 从「说完」起算）。探针喂帧不等实时（root 前仅 89ms），
  **别把 89ms 当判停**——真人 500ms 见 `docs/验收-本机真人-20261010.md`。

**尾部那一轮（1204ms）的解剖**：`tts.connect` 263（冷路径）+ `llm.headers` 411 + `first_byte` 375；
池快照 `warm=5 / cold=1 / prewarm_fail=1` —— **一次预热失败**就吃掉 ~213ms。
⇒ 已给预热加**一次重试**（`WARM_RETRY_DELAY_S=0.15`：重试只让到位晚 150ms，
而一次失败让整轮多付 213ms）；仍失败才计数并退回冷路径，单测
`test_prewarm_retries_once_after_transient_failure` 钉住。

## 五、根因（按"离 300ms 的距离"排）

| # | 根因 | 证据 | 性质 |
|---|---|---|---|
| 1 | **TTS 首片是地板，其中建连那一格已去**：本地 melo/kokoro 无增量流（melo ~70ms/字）；云流式首片 604ms = **建连 259ms（每句新建合成器，连接不复用）+ 服务端首字节 338ms** | §三表 + §四 4.1/4.4 + `probe_tts_firstchunk.py` | 服务端首字节是架构天花板；**建连已由 P0.5 连接预热去掉**（`tts.connect` 257→38ms、每会话首轮 1317→777ms；稳态 A/B 在噪声内，见 §四 4.4） |
| 2 | **服务端首字节 ~338ms 与字数无关**（1 字 419ms vs 25 字 351ms，噪声内） | §四 4.1 | 服务端首块策略，只能换服务商/换流式协议 |
| 3 | **LLM 首 token 284ms 几乎全在网关侧**：`llm.prefill` 仅 0.1ms，同主机静态端点 ttfb 就要 208ms；且 qwen-flash 已是全平台最快（新 flash 全是推理型，ttft 2.8~11.3s） | §四 4.1/4.2 | 换模型方向相反；只有换部署位置才动得了 |
| 4 | **判停 500ms 不进口径B 但计入体感**：conservative 档的静音窗 | `eou_latency_ms` p50 506~514ms | 体感项，与"不抢话"直接 trade-off |
| 5 | **上行抢循环 ~4%**：判停后客户端仍在喂帧，每帧 `np.concatenate` + 线程派发 ≈ 2.7ms | §三"上行帧 CPU"行 | ✅ **P1 能量门已落地**（2026-10-17）：同时段 A/B 口径B p50 −97/−113ms，比预估的 ~40ms 更多，见 §四 4.5 |
| 6 | **LLM 与 TTS 没有真正并行**：serial 在 `llm.astream` 循环体内 `await` 合成，LLM 生成被合成阻塞 | `llm.request` 嵌套 `tts.synth` | 影响**总时长**，不影响首音 |

### 一句话结论

**当前架构下口径B 的地板 ≈ 服务端首字节 ~320ms + LLM 网关 ~230ms + 首句 ~120ms
≈ 700ms**（云流式 + qwen-flash，建连已由 P0.5 预热去掉，§四 4.4 实测 724ms），
与 300ms 差 2.3 倍。剩下能动的只有三处：把 TTS 首片搬进用户说话时段（投机，
实测命中率 4%，净负债）、换首包更快的流式 TTS、把 LLM 部署搬得离网关更近。
**这不是调参问题，是时序模型问题。**

## 七、对照文章（mp.weixin.qq.com/s/e34VgNJPT3qc7ofgSn1afw）的启发

文章是本仓配套的那篇《给AI产品接上嘴》。逐条对我们有用的 / 站不住的：

### 有用的启发

| 文章的做法 | 我们的现状 | 可借鉴点 |
|---|---|---|
| **第一板斧：分句合成**，且代码用 `asyncio.create_task(tts_speak(...))` | 我们 `await` 在 LLM 循环体内（串行） | **机制上文章更并行，但不等于更快被听见**：首音不受益；墙钟会短（推算 ≈ 后句合成时长），而**感知收益只在后句比前句长的时候出现**——本仓 2 句轮实测为 −86ms（音频已提前就绪，只是堆在客户端缓冲）⇒ **P4 不作为优化项** |
| **第二板斧：连接预热 / WarmPool**（预建 WS、预合成 20ms 静音让播放器进推流就绪） | **连接预热已兑现**（P0.5，§四 4.4：`tts.connect` 257→38ms、首轮 1317→777ms；稳态 A/B 在噪声内）；「预合成静音帧」仍未做（差距表在列）；httpx 连接复用已有 | 文章的 400ms 数字仍存疑，但**方向这次被我们的实测证实**：云流式首片 604ms 里 259ms 是建连，预连后首片 406ms（§四 4.4）。文章值得学的不是数字，是"连接也是延迟账的一格" |
| **第三板斧：音频参数**（24k、200ms 片、只压协议头） | 已实现 | 无新信息；本机 `tx.first_audio` 0.08ms 证明不在瓶颈上 |
| **barge-in 三层**：回声抑制（播放文本↔ASR 结果重合即丢弃） | 只有 L1 能量 + L3 状态机 | **这是文章最值钱、我们最缺的一层**。判据 8（真人干净度）/判据 10（回声）都卡在这。文章的判据（"识别结果与播放中的内容高度重合"）可以直接实现成文本包含度 |
| **barge-in 第二层：意图分类**（「嗯」 vs 「等等你说错了」） | 未实现（L3 文本路 turn-detector 未接） | 方向一致，二期 |
| **状态机统一取消**（打断先走统一取消例程） | ✅ `turn_fsm` + outbox + `AudioStop` | 文章的竞态警告（播放队列没清干净 → 幽灵尾音）我们已踩过并量化（尾音量化脚本） |
| **文章的口径选择**：目标是"体感"（「像在跟客服排队」），不是技术指标 | 我们分口径A/B + 体感首音 | **文章这一点是对的**，也是 filler 合法性的来源。但文章把体感数字和技术口径混着报，我们不许 |

### 站不住的点（文章要改口，或我们不许跟着错）

1. **文章的账自己加不起来**：200（ASR）+ 500（LLM）+ 250（TTS）= **950ms ≠ 300ms**。
   本仓实测也不支持 300ms：口径B 地板 ~0.7s，体感（含判停）~1.2s。
2. **文章全程没有"判停"这一项**，而它是"敢不敢不抢话"的那 500ms——
   恰是体感里最大的一块之一。
3. **"ASR 首字 200ms"** 在 chunk 式模型上有天花板（本机 paraformer 600ms / zipformer 300ms）。
4. **"TTS 首包 250ms"**：本机实测云流式 604ms（其中建连 259ms）、本地 melo 1526ms。
5. **"连接预热省 400ms"**：我们这边数字更小也更实——预热去掉的建连是 259ms/句，
   `tts.connect` 实测 257→38ms、每会话首轮 1317→777ms（同期 A/B 稳态 724 vs 700ms
   在噪声内；1029→724 是跨时段对比，§四 4.4）。文章这条从"存疑"改判为
   **"方向正确、数字比它说的小"**。

> 结论：文章的**方法**（拆开流式、三板斧、barge-in 分层）值得学；
> 文章的**数字**（300ms 与各项分解）在本机不可复现，已在
> `docs/优化空间-20261010.md` §四列出要改的口。
