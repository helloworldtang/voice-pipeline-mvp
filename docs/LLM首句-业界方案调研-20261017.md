# LLM 首句这一格：业界方案调研（2026-10）

> 问题：口径B 里最大的一格现在是 LLM——`prefill 66~141 + 首句 74~105 = 180~245ms`，
> 是 TTS（~50ms）的 2~5 倍。这份文档分四层调研：架构、模型、推理工程、协议，
> 最后给"我们能做什么、按什么顺序、什么时候停"。

## 0. 坐标：我们已经比公开的级联方案快 2~4 倍

| 方案 | 首包延迟 | 来源 |
|---|---|---|
| 公开级联分析（首 token 350~1000ms + TTS 75ms） | **775~1425ms** | 知乎《AI 语音处理10》，2026-06 |
| 豆包端到端实时语音（API） | ~**700ms** | 火山引擎产品页 |
| 本仓（mlx 1.5B + 讯飞 TTS，n=11） | **306ms**（p50） | 本仓实测 |
| Qwen3-Omni（开源端到端，理论值） | **234ms** | 技术报告 |

结论先说：**继续压是"从好到很好"，不是"从不可用到可用"**。所以每条方案都要算 ROI，
过不了 kill criteria 就不做——这和本仓"否定也要成文"的规矩一致。

## 1. 架构层：三段级联 vs 端到端语音模型

| | 级联（我们） | 端到端（Qwen3-Omni / 豆包实时语音） |
|---|---|---|
| 延迟构成 | ASR + LLM + TTS 三段，每段有边界 | 单模型，音频进音频出，无边界 |
| 理论下限 | 三段固定开销相加（我们 ~300ms） | 234ms（Qwen3-Omni 冷启动理论值） |
| 实测 | 306ms（本机） | 631~655ms（vLLM-Omni，**并发 64**，3 GPU）；豆包 API ~700ms |
| 代价 | 三段可分别替换/降级 | 30B-A3B MoE，需 GPU 或按量付费；本地 Mac 跑不动 |
| 可控性 | 高（TTS 换厂、LLM 换模型都是局部改动） | 低（换模型=换整套，判停/打断语义要重写） |

**判断**：端到端在"理论"上更快，但**公开可得的实测值（631ms@并发64、700ms@API）比我们现在的 306ms 还慢**。
它真正的优势是韵律自然、无边界感，不是首包。且 Qwen3-Omni 的 234ms 是"纯模型、冷启动、无排队"，
和产品口径不是一回事。

→ **不进本轮范围**。等出现"单请求实测 ≤250ms 且中文可用"的端到端服务再评估。

## 2. 模型层：2026 年的小模型

| 模型 | 规模 | 特点 | 对我们的意义 |
|---|---|---|---|
| Qwen3.5-0.8B / 2B / 4B / 9B | 0.8B~9B | 2026-03 开源，**混合注意力（75% 线性 + 25% 全注意力）**，KV cache 降 ~75%，原生多模态，256K 上下文 | 同尺寸下更强的候选；2B 是"日常助手甜点位" |
| Qwen3-Omni-30B-A3B | 30B MoE (3B 激活) | 端到端语音，Apache 2.0 | 见 §1，本机跑不动 |
| Qwen3.8 系列 | 2.4T MoE 起 | 2026-08 旗舰 | 与本机无关 |

**实测 A/B（本机 MLX，同一 system prompt、同一问句、各 3 次）**：

| 模型 | TTFT | 首句 | 回答长度 | 备注 |
|---|---|---|---|---|
| Qwen2.5-1.5B-4bit（现用） | **46ms** | **88ms** | 15 字 | 微基准 |
| Qwen3.5-2B-4bit | 50ms | 88ms | 21 字 | 微基准；**必须关思考链** |
| Qwen3.5-0.8B-4bit | **32ms** | **61ms** | 14 字 | 微基准；同样要关思考链 |

但**进链路后是另一回事**（`VOICE_LLM_MLX_MODEL=Qwen3.5-2B-4bit`，讯飞 TTS，5 轮）：

| | prefill | 首句 | 口径B p50 |
|---|---|---|---|
| Qwen2.5-1.5B | 66~141 | **74~105** | **306** |
| Qwen3.5-2B | 139~156 | **164~165** | 546 |

原因不是模型慢，是**它话更多**：首句 21 字 vs 15 字，加上 2B 解码更慢，首句多花 ~70ms。
质量确实更好（回答更完整），但**在"首句要多快"这个指标上，2B 是负收益**。

**但 0.8B 是正收益**（同一链路、同一讯飞窗口，6 轮）：

| | prefill | 首句 | tts.first_chunk | 口径B p50 |
|---|---|---|---|---|
| Qwen2.5-1.5B（现用） | 66~141（中位 118） | 74~105（中位 75） | 48~53（好档窗口） | 306 |
| Qwen3.5-2B | 139~156 | 164~165 | 195~306 | 546 |
| **Qwen3.5-0.8B** | **51~81（中位 56）** | **38~39** | 116~349（当轮是慢档） | **259** |
| **Qwen3.5-0.8B（复测，讯飞快档）** | **56~74** | **34~36** | **41~60** | **167**（n=5，158~195） |

LLM 这一格（prefill + 首句）：1.5B **193ms** → 0.8B **94ms**，**−100ms**（这一格可比）。

口径B 受讯飞档位影响很大，同配置两次测出 259（慢档）与 **167**（快档）——
两项叠加后，**0.8B + 预建连 + 快档 = 167ms**，慢档约 270ms。

**质量的代价（4 题抽检，同一 system prompt）**：

| 问题 | Qwen3.5-0.8B | Qwen2.5-1.5B |
|---|---|---|
| 鲁迅认识周树人吗 | "是的，鲁迅认识周树人" | "认识。鲁迅是周树人的笔名" ✅ 更准确 |
| 树上 10 只鸟打 1 只剩几只 | 9 只 | 9 只（都掉了陷阱） |
| 37×24 | 888 ✅ | 888 ✅ |
| 上海现在适合穿什么 | "休闲舒适的日常服装"（笼统） | "长袖长裤，避免短袖短裤" ✅ 更具体 |

结论：**0.8B 换得来 ~100ms，代价是回答变笼统/偶发不准确**。这是产品取舍，不是纯工程问题，
所以**没有擅自换默认**（改默认 = 静默降质，违反"不影响体验才执行"）。用法：
`VOICE_LLM_MLX_MODEL=mlx-community/Qwen3.5-0.8B-4bit`。

> **坑（已验证）**：Qwen3.5 默认开思考链——同一句问话，60 token 内全是
> "Thinking Process: 1. Analyze the Request…"，一句人话都没有。语音助手必须传
> `enable_thinking=False`（已在 `mlx_llm._apply_template` 落地，老模板不认该参数时自动退回）。

## 3. 推理工程层：逐条对照我们的场景

我们的事实基础：**prompt 只有 39 token**（system 30 + 问句 9），模型 1.5B/4bit，单用户。

| 手段 | 业界的收益 | 对我们 |
|---|---|---|
| Prompt / prefix caching | 1k token 时只省 **7%** TTFT，150k 才 67%（tianpan, 2026-04） | **≈0**：39 token 没有可省的空间；只有多轮长历史才有意义 |
| Chunked prefill / 分离式 prefill-decode | 提升吞吐、压长 prompt 的 TTFT | 服务器侧手段，单请求本机无收益 |
| Speculative decoding | 提高 decode tok/s | 不降 TTFT（要先生成 draft），对"首句"无效 |
| CUDA Graph / kernel 融合 | vLLM-Omni 里 TTFP 5884→2790ms | NVIDIA 侧手段；MLX 上无对应开关 |
| 量化 | 4bit 已是甜点 | 已做 |
| **进程隔离（避 GIL）** | — | **有实证**：同样代码，TTS 的 `tts.first_chunk` 在 MLX 线程同时跑时从 216→411ms。LLM 侧同理会把 45ms 的微基准抬到 66~141ms |
| 首句更短（护栏/提示词） | 线性 | 已实测 −31ms（`VOICE_FIRST_SENTENCE_MAX_CHARS`），代价是逗号收尾的语调 |

## 4. 结论与建议顺序

**能动的只有三处**，按 ROI 排：

1. **LLM 出进程（独立进程 + 流式 IPC）** —— 唯一还有两位数收益的工程手段。
   现状证据：微基准 46ms → 链路内 prefill 66~141ms，差值基本是 GIL/线程调度。
   预期 −20~60ms。改动中等（新增进程 + 传输），可回退（env 切回进程内）。
   **kill criteria**：做完后 p50 降幅 <15ms 就回滚并记否证。
2. **首句护栏**（−31ms，已实现，默认关）—— 代价是逗号收尾的语调，需要人耳验收。
   **kill criteria**：试听认为语调不自然就不开。
3. **换 0.8B**（LLM 格 −100ms，口径B 约 230~265）—— **技术上是现成开关**，
   但会牺牲回答的具体度（见 §2 质量表）。要不要把它做成默认，是产品决定，等你定。

**不做的**（都有明确理由，见上）：端到端语音（实测比我们慢）、prompt caching（39 token）、
speculative decoding（不降 TTFT）、chunked prefill（服务器侧）。

## 4.1 附：LLM 出进程的实测结果——**否证**（触发 kill criteria）

按上一节的第 1 项做完了，结论是它**不解决问题**，如实记录：

实现：`providers/llm/mlx_worker.py`（子进程：加载一次、逐 token 出、支持取消）
+ `providers/llm/mlx_proc_llm.py`（父侧：流式 IPC，同 `LlmProvider` 契约），
开关 `VOICE_LLM_PROCESS=1`。

| 量 | 进程内 | 子进程 |
|---|---|---|
| 微基准 TTFT | 46ms | **34~36ms**（子进程内部）/ **46ms**（父侧，IPC ≈12ms） |
| 链路内 `llm.prefill` | 66~141（中位 118） | 77~140（中位 115） |
| 链路内 `llm.first_sentence` | 72~105（中位 75） | 74~77（中位 75） |
| 口径B | 306（好档窗口） | 308~466（**该窗口讯飞是慢档，TTS 134~254**，不可比） |

**判读**：拆进程让"模型自己"确实更干净（34ms vs 46ms），但**链路内 LLM 那一格纹丝不动**。
说明 `prefill 66~141` 里超出微基准的那 ~70ms **不是 GIL**——GIL 的解释对 TTS 成立
（`tts.first_chunk` 216→411 有对照），对 LLM 不成立。

按预设的 kill criteria（降幅 <15ms 即回滚）：**默认关闭**（`VOICE_LLM_PROCESS` 不带默认值）。
代码保留：协议与 provider 契约是干净的，将来把模型挪到别的机器/GPU 上可以直接复用。

**剩下的真实空间**：`llm.prefill` 的 115ms 中位里，模型只占 ~35ms，
其余 ~80ms 花在"拿到句子 → 派发 → 收到首 token"这段编排上。要再压就得动调度器/指标口径，
而不是换模型或换进程。

## 4.2 附：miss 路径 cancel 修复的 A/B——**延迟假设否证，卫生修复保留**

上面的悬案引出一个假设：miss 轮的 fallback 会不会在排队等**没被取消的作废投机生成**
（修复前 cancel 只有三处调用，miss → fallback 路径确实漏了）。修了之后用
SimAsr 错前缀 + 真 MLX 1.5B 做了 A/B（`scripts/ab_miss_prefill.py`，各 n=8）：

| EOU 前投机跑了多久 | 修复前 prefill p50 | 修复后 prefill p50 | 差值 |
|---|---|---|---|
| 300ms（作废生成近尾声） | 59.4 | 49.9 | −9.5 |
| 100ms（争抢窗口最大） | 48.4 | 49.1 | ≈0 |

**判读（kill criteria <10ms 触发，如实记否证）**：

1. "miss 轮 prefill 被 ~80ms 拖累"**不成立**——两条并发 `stream_generate` 在 Metal
   队列上交错，39 token 的 prefill 太小，争抢代价 ≈ 0~10ms（噪声量级）。
2. 更有信息量的是修复后的深拆：`llm.worker_ttft` p50 48~49 / `llm.wakeup` p50
   **0.8~0.9ms**——**sim 环境里 prefill ≈ 纯生成，那 80ms 根本不存在**。
   ⇒ 真链路 115ms 里的差值来自 sim 没有的负载：真 ASR 的 ONNX 解码线程、
   100ms 一帧的上行、真 TTS websocket。归属要真人链路上看 `llm.wakeup` 格：
   wakeup 大 = loop 拥堵（动调度）；worker_ttft 大 = 算力争抢。
3. **修复保留**：它兑现的是调度器纪律三（作废即取消、不白烧 CPU——修复前作废
   生成会白跑到 EOS），价值在功耗/发热/纪律，不在延迟。stop 旗标（`mlx_llm`）
   让 cancel 真能停线程，`to_thread` 的 cancel 本身停不了。

## 4.3 模型从哪拉：ModelScope 优先

HF 镜像在本机有两个坑：Xet 后端 401、关掉 Xet 后仍然慢。改用 MapScope 同名镜像：

```bash
uv run --with modelscope python scripts/fetch_model.py --repo mlx-community/Qwen3.5-0.8B-4bit
# → /Users/.../modelscope/models/mlx-community--Qwen3.5-0.8B-4bit/snapshots/master
VOICE_LLM_MLX_MODEL=<该路径> ./scripts/dev_server.sh
```

实测 625MB **100 秒 / 14.5MB/s** 下完；`model.safetensors` 的 sha256
与 HF 版**逐字节一致**（`f5a0d9dd…`），不存在"国内源是另一个模型"的风险。
本地路径加载比走 HF cache 还快一点（微基准 28ms vs 32ms，首次少一次 cache 查找）。
