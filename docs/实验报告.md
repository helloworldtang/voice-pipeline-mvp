# 实验报告：300ms 到底成不成立

> 这份文件是技术方案 §9 里程碑表里列的 M4 验收物，此前一直缺失（`docs/` 整个目录都没有）。
> 它回答的只有一个问题：**口径B（用户说完 → AI 首音）能不能做到 300ms 级。**

- 日期：2026-09-22
- 机器：arm64 / macOS 26.6.2 / Python 3.12.13
- 原始数据：`bench/ab-20260922-repeat3.json`（sim）、`bench/ab-20260922-qwen.json`（真 LLM）、`bench/ws-20260922-smoke.json`（WS 链路）

---

## 一、结论（先说答案）

**不成立。而且不是差一点，是差一个数量级的机制。**

| | serial（对照） | pipelined（投机） | 命中率 | 投机净收益 |
|---|---|---|---|---|
| **SimLlm**（零延迟替身） | p50 **770ms** | p50 **842ms** | 9/36 = **25%** | **−72ms（赔）** |
| **QwenLlm**（qwen-flash 真网络） | p50 **1840ms** | p50 **2491ms** | 1/24 = **4%** | **−651ms（大赔）** |

三件事必须一起说，拆开任何一件都会误导：

1. **300ms 在任何一组里都达不到最好那一轮之外的位置。** 真 LLM 下唯一一次进 600ms 以内的是 534ms，占 1/24。
2. **投机执行在本实现下是净负债，不是优化。** 它改善均值、恶化中位数：把分布拉成双峰（少数人 0~534ms，多数人 870~3312ms）。
3. **`SimLlm` 的数字不能用来论证投机可行。** 换真 LLM 后命中率从 25% 塌到 4%——因为零延迟替身让投机"跑得完"，真 LLM 跑不完。

> 这三条合起来，就是 README 里那句「179ms」真正的代价：它是 **sim LLM + 挑最好一轮** 的产物。

## 二、实验设计

### 变量

| 变量 | 取值 | 说明 |
|---|---|---|
| 调度器 | `serial` / `pipelined` | 唯一自变量，其余依赖完全相同 |
| LLM | `SimLlm`（0ms） / `QwenLlm`（真网络） | **关键变量**：决定投机跑不跑得完 |
| 静音窗 | 250ms / 600ms | 用户说完后的静音长度，250ms 贴近真实 |
| `grace_ms` | 0 / 300 / 600 | EOU 后最多再等多久让投机落地 |
| 句长 | 3 句（7 / 12 / 20 字） | 长句更难在窗口内跑完 |
| 重复 | 2~3 轮 | 用来算分位数，不是用来挑最小值 |

### 两条链路，各自回答什么

| 链路 | 命令 | 含什么开销 | 不含什么 |
|---|---|---|---|
| `bench_schedulers.py` | 进程内直接调调度器 | ASR/TTS 真实推理 | **不含 EOU 判停开销、不含网络与序列化** |
| `bench_ws.py` | 真 uvicorn 进程 + 真 TCP + JSON | 上述全部 + 服务端 `FusedEou` 自动判停 | — |

⚠️ `bench_schedulers.py` 是**手动补静音窗**代替 `FusedEou` 的，所以它的数字里没有判停成本。
这就是为什么还要有 `bench_ws.py`——判停那一段是口径B 残余间隙里的大头，不算进去等于少算一格。

### 判据：为什么报 p50 而不是 min

本项目纪律是「不裁剪、不挑轮次」。旧版 `bench_schedulers.py` 在 `--repeat` 时**只保留 caliber_b 最小的那一轮**
（`if best is None or row.caliber_b_ms < best.caliber_b_ms: best = row`）——那是脚本内置的挑选器，
谁复跑谁拿到一个被挑过的数字。已改为全轮保留，由报告脚本算 p50 / min / max。

## 三、结果

### 3.1 SimLlm（零延迟替身，n=36 pipelined / 18 serial）

```
serial    口径B p50  770ms
pipelined 口径B p50  842ms   → 比串行慢 72ms
命中率 9/36 = 25%
  命中时    p50    0ms   （min 0）
  未命中时  p50  870ms   （max 1166）
```

按静音窗拆开（关键：25% 这个总数被 600ms 长静音窗拉高了）：

| 静音窗 | 命中率 | 命中时 p50 | 未命中时 p50 | 比 serial 慢 |
|---|---|---|---|---|
| 250ms（贴近真实） | 3/18 = **17%** | 81ms | 854ms | +85ms |
| 600ms | 6/18 = 33% | 0ms | 1000ms | +228ms |

`grace` 的代价在 250ms 组看得最清楚：

| grace | 命中 | 命中时 p50 | 未命中时 p50 |
|---|---|---|---|
| 0 | 0/9 | — | 841ms |
| 300 | 3/9 | 81ms | **1150ms** |

> `grace` 是赌注：不加则永远不命中（0/9），加了则未命中时白等（+300ms）。
> **没有免费的窗口。**

### 3.2 QwenLlm（qwen-flash，含真实网络，n=24 / 12）

```
serial    口径B p50 1840ms
pipelined 口径B p50 2491ms   → 比串行慢 651ms
命中率 1/24 = 4%
  命中时    p50  534ms  （唯一一次）
  未命中时  p50 2491ms  （max 3312）
```

同矩阵（grace=300）下的直接对比——**这是本报告最硬的一张表**：

| 静音窗 | LLM | 命中 | 口径B p50 |
|---|---|---|---|
| 250ms | SimLlm | 3/9 | 1140ms |
| 250ms | **QwenLlm** | **0/6** | **2316ms** |
| 600ms | SimLlm | 3/9 | 1134ms |
| 600ms | **QwenLlm** | **0/6** | **2491ms** |

真 LLM 下唯一命中的那一轮：`今天天气怎么样` + 静音窗 600ms + grace 600ms → **534ms**。
它需要的窗口是 1200ms（静音窗 600 + grace 600），而真实对话里没人说完还静音 600ms。

### 3.3 为什么真 LLM 一上，命中率就塌了

投机的命中条件是：**在「静音窗 + grace」这段时间内跑完 LLM 首完整句 + TTS**。

真 LLM 的实测成本（见 `scripts/probe_llm.py`）：`qwen-flash` 首完整句 **522ms**（±121ms），TTS 另需 ~200ms。

| 窗口 | 需要 | 够不够 |
|---|---|---|
| 250 静音 + 300 grace = 550ms | 522 + 200 = 722ms | ❌ 不够 → 0/6 |
| 250 静音 + 600 grace = 850ms | 722ms | ⚠️ 边缘，被 LLM 波动打穿 → 0/6（同矩阵未跑 600） |
| 600 静音 + 600 grace = 1200ms | 722ms | ✅ 够，但仍只有 1/2（LLM 波动 ±121ms） |

**这就是结论的机制**：不是实现写得不好，是 **LLM 首 token 那一格比静音窗能提供的窗口大**。
要买命中率只能加大 `grace`，而 `grace` 在未命中时是纯亏损——两头一挤，期望值为负。

### 3.4 WS 链路（真 uvicorn + 真 TCP，n=6，修复判停后）

⚠️ **样本量小，不能用于结论，只用于验证「实验组在真实链路上真的能跑」+ 量判停那一格。**

| 句 | mode | 口径B | 判停延迟 | 命中 |
|---|---|---|---|---|
| 今天天气怎么样 | real-serial | 2111ms | 296ms | — |
| 今天天气怎么样 | real-pipelined (grace 0) | 1994ms | 296ms | 0 |
| 今天天气怎么样 | real-pipelined (grace 300) | 2298ms | 296ms | 0 |
| 我想问一下明天的天气怎么样 | real-serial | 2753ms | 282ms | — |
| 我想问一下明天的天气怎么样 | real-pipelined (grace 0) | 2644ms | 282ms | 0 |
| 我想问一下明天的天气怎么样 | real-pipelined (grace 300) | 3104ms | 282ms | 0 |

- ✅ `pipelined` 确实能在 wire 上被选中并跑完（此前 wire 上只有 `echo|serial|real`，已修）。
- ✅ 服务端 EOU 自动判停可用，判停延迟 **282~296ms**（6 轮中 5 轮自动判停，1 轮超时兜底）。
- ⚠️ 口径B 比 `bench_schedulers` 的同组更大（2432 vs 1840），因为判停越早，
  LLM+TTS 的时间就越完整地落在 `utterance_end` 之后——这是口径本身决定的，不是退步。

### 3.5 修复：semantic 档曾完全失效（本次排查挖出来的真 bug）

首轮 WS 实测曾报「2/4 轮 EOU 漏判」，我一度归因为「synthetic 语音 + semantic 档不稳」。
**这个归因是错的**，逐格探针（`scripts/probe_eou.py --trace`）给出的真因是两个数字互相打架：

| 位置 | 数值 | 含义 |
|---|---|---|
| `ProsodyEou.coda_ms` | 250 | 静音**超过** 250ms 就主动清零终顿（纯静音不提供信息） |
| `FusedEou.min_silence_short_ms` | 250 | semantic 档静音**至少** 250ms 才去读终顿 |

100ms 帧粒度下，静音只取 0/100/200/300…，`[250, 250]` 这个交集**永远采不到样**：

```
时刻   静音    韵律终顿
1600    200    True      ← 终顿成立，但静音不够 250
1700    300    False     ← 静音够了，终顿已被 coda 清掉
...     ...    False     ← 一路等到 2000ms 看门狗
```

结果：semantic 档退化成「等满 2000ms 看门狗」，实测判停延迟 **1804ms**。
**终顿是事件不是状态，却按瞬时状态来读** —— 已改为锁存最近一次终顿时刻，按
`terminal_window_ms`（默认 400ms）判定。修复后判停延迟 **1804ms → 87~123ms**（离线探针）、
**282~296ms**（WS 端到端）。

同时修掉一个让该指标「看起来正常」的坑：`Session.run_turn` 在 `finish()` **之前**就
`eou.reset()`，而 `eou_latency_ms()` 读的是已被清空的静音计时 → 账单里恒为 **0**。
0 长得像个正常数字而不像缺失，所以这个失效潜伏了整个里程碑。已改为 reset 前采集。

> 教训：**0 比 −1 危险。** 缺失值若写成 0，没人会去查它为什么是 0。

> ⚠️ **一处自我更正**：本节首句提到的「2/4 漏判」，我最初写进 MEMORY 时归因为
> 「synthetic 语音 + semantic 档不稳，是换档的第一个反证」。逐格实测证明那是**错的**——
> 主因是上面的判据互斥 bug（已修）。测量方式也有一份责任：旧版 `bench_ws.py`
> 发完 250ms 静音就停止喂帧，而真实麦克风在用户闭嘴后仍在送帧，静音累计会持续增长。
> 两者叠加才造出「漏判」的观感。**修复后 6 轮里 5 轮自动判停。**

## 四、对外的三个数字该怎么说

| 场景 | 该说的 | 不该说的 |
|---|---|---|
| 本机侧下界（无 LLM） | 「serial p50 770ms」 | ~~713ms~~（那是单轮最好值） |
| 含真 LLM 的端到端 | 「serial p50 1840ms，最快 1672ms」 | ~~179ms / 81ms / 534ms~~ |
| 投机执行的收益 | 「命中率 4%，常态比串行慢 651ms」 | ~~把 TTS 藏进尾段就能到 300ms~~ |

一句话版本：

> **300ms 在真 LLM + 自动判停的端到端链路上不成立。** 本机实测最好 1672ms（WS）／1840ms（p50）；
> 投机执行能把少数轮次压到 534ms，代价是常态变慢 651ms，命中率 4%。

## 五、这份报告的边界（必须一并引用）

1. **上行是 TTS 合成语音，不是真人录音。** 数字用于比较调度器之间的**相对差值**，不是真人场景绝对值。
   合成语音的韵律与真人有差，直接影响 EOU 判停（见第 3 条）。
2. **口径A（用户开口 → AI 首音）恒空。** `vad_onset` 全仓从未打点，`providers/vad.py` 的 SileroVad
   只喂给 `demo_real.py`，没进 metrics。文章标题那个口径目前**测不出来**，不是测出来很差。
3. **EOU 判错率仍未实测（这是当前最大的开口）。** 默认档位已由 conservative 切到 semantic，
   换档依据是**机理**不是中文实测。更关键的是：本次修复把终顿从「瞬时读取」改成「锁存 400ms」，
   判停因此**更早更容易触发**——**抢话率（`premature_eou`）必然上升，但上升多少没有数**。
   真人说话的词间停顿常在 200~400ms，正好落在新判据的触发区。
   D4（错误率–延迟曲线）、D5（中文测试集）未闭环前，**semantic 档不应作为对外默认承诺**。
4. **WS 链路 n=6**，只证明可达与判停量级，不证明端到端的统计显著性。
5. **SimLlm 组与 QwenLlm 组的矩阵不完全相同**（sim 跑了 grace 0/300，真 LLM 跑了 300/600），
   已用共同的 grace=300 格子做公平对比，但两组样本数不同（9 vs 6）。
6. **本次修复未做真人回归。** 所有判停数字都来自 TTS 合成语音，合成语音的尾部能量轮廓
   比真人干净，判停延迟 282ms 在真人场景下大概率**偏乐观**。

## 六、复现

```bash
# 零延迟替身：看调度器结构差异（快，约 4 分钟）
uv run python scripts/bench_schedulers.py --tts melo \
    --silence-ms 250,600 --grace-ms 0,300 --repeat 3 --json-out bench/ab-sim.json

# 真 LLM：看真实网络下的命中率（约 4 分钟，需 DASHSCOPE_API_KEY）
uv run python scripts/bench_schedulers.py --llm qwen --tts melo \
    --silence-ms 250,600 --grace-ms 300,600 --repeat 2 --json-out bench/ab-qwen.json

# WS 链路：含网络与服务端自动判停（每个连接重载模型，慢）
uv run python scripts/bench_ws.py --silence-ms 250 --grace-ms 300 \
    --repeat 1 --modes real-serial,real-pipelined

# LLM 选型本身（首 token / 首完整句 / 思考链）
uv run python scripts/probe_llm.py --runs 3
```

⚠️ `bench_ws.py` 每次新建 WS 连接都会重建 Session，而真模型**没有加载缓存**，
所以每个组合都要付一次模型加载时间——这是它比 `bench_schedulers.py` 慢的主因，不是链路开销。
