# 流程拆解与优化空间

回答三个问题：时间花在哪、流程能不能并行、每一格还有没有得榨。
所有数字都来自本机实测，附复现脚本。

> 与 `docs/实验报告.md` 的分工：那份是**数字账本**（每个结论的样本量与边界），
> 这份是**架构视角**（哪一步等哪一步、天花板在哪）。数字冲突时以实验报告为准。

## 一、完整链路（real-serial，当前默认）

```
用户说话 ──► [ASR 流式识别] ──► partial 文本 ──┐
     │                                          │ 每帧都喂
     └────────► [EOU 判停器] ──► 判停？────────┘
                                    │ 是
                                    ▼
                          asr.finalize()          ← 实测 0.1ms，免费
                                    ▼
                          LLM astream()           ← 首 token 345ms
                                    ▼
                          SentenceSplitter.feed() ← 首句成 48ms
                                    ▼
                          tts.synth_blocking()    ← 整句阻塞 1156ms
                                    ▼
                          Chunker.feed() → 200ms 片
                                    ▼
                          首音下发
```

关键：**除 ASR 与 EOU 是跟说话并行的，其余全部严格串行**。
串行链是 `finalize → LLM → 分句 → TTS`，前一步不出结果后一步不动。

## 二、时间花在哪（melo 引擎，n=6，口径B p50 1602ms）

| 段 | 实测 p50 | 占比 | 性质 |
|---|---|---|---|
| 判停 | 100ms | 6% | 神经档，已近地板 |
| 判停 → LLM 首 token | 345ms | 21% | 云端 API RTT + prefill |
| LLM 首 token → 首句成 | 48ms | 3% | 流式分句，几乎免费 |
| **首句成 → TTS 首片** | **1156ms** | **70%** | **整句阻塞合成** |
| TTS 首片 → 首音下发 | 0ms | 0% | 已在同一时刻 |

kokoro 对照（n=6）：TTS 那格 1472ms，口径B 1792ms。换引擎省 316ms。

**TTS 单独占七成，比其余三格加起来还大。**

## 三、流程有没有并行机会

### 3.1 已经并行的

| 已并行 | 说明 |
|---|---|
| ASR 与用户说话 | 流式，边说边识别 |
| EOU 与用户说话 | 边说边判停 |
| TTS 计算与事件循环 | `asyncio.to_thread`，不堵循环 |
| 下行发送与上行收帧 | outbox 队列，barge-in 才能工作 |

### 3.2 试过但失败：投机执行（pipelined）

思路：用户还没说完就用 partial 去跑 LLM+TTS，判停后直接播。

**实测命中率 4%，常态比串行慢 651ms（净负债）。**

根因（本次新测，`scripts/` 无对应脚本，见下文复现）：
**ASR 的 partial 直到语音最后一刻才等于 final。**

| 语音时长 | partial 首次 = final | 投机窗口 |
|---|---|---|
| 1596ms | 1400ms | 说完前 196ms |
| 2024ms | 2124ms | **说完后 100ms（静音期才补齐）** |
| 3001ms | 3000ms | 说完前 1ms |

最后 1~2 个字必然在静音期才吐出。而校验要求「投机时的 partial == 判停后的 final」——
这个条件在判停那一刻几乎不可能成立。

⇒ **命中率 4% 是原理性的，不是 grace/debounce 参数没调对。**
要放宽校验（允许尾部几个字不同）才能提命中率，代价是对"错问题"给出流利答案——
这是产品取舍，不是技术优化。

### 3.3 还没试的并行

| 机会 | 预期收益 | 可行性 |
|---|---|---|
| **TTS 增量流**（边合成边吐） | 首片可省 800ms+ | ❌ 本机两引擎都是**整句一次性回调**（melo/kokoro 均只回调 1 次，实测） |
| 多句并行合成 | 0（不影响首音） | 可行但无用 |
| LLM 边出边合成 | 已实现（分句即合成） | — |

**TTS 无增量流是架构天花板**：首音必须等第一句整句合成完。
要突破只能换支持流式的 TTS 模型（如 CosyVoice2 / IndexTTS 的流式变体）。

## 四、每一格还有没有得榨

| 格 | 现状 | 还能榨吗 |
|---|---|---|
| 判停 | 100ms | 已近地板。再快就要牺牲抢话率（官方集 4.6%） |
| ASR finalize | **0.1ms** | 无空间，本来就是免费的 |
| LLM 首 token | 345ms | 云端硬底。system prompt 只有 42 字，不是 prefill 的锅；换更快的模型是唯一路 |
| 分句 | 48ms | 无空间 |
| **TTS 首片** | 1156ms | **唯一有真实杠杆的一格** |

### TTS 那一格的两个杠杆

**杠杆 A：首句字数**（实测，melo，n=5，min/p50/max 一致）

| 文本长度 | 3字 | 7字 | 10字 | 24字 | 52字 |
|---|---|---|---|---|---|
| 合成耗时 | 287ms | 570ms | 886ms | 1995ms | 4214ms |

拟合：**固定开销 ≈ 80~100ms + 边际 ≈ 79ms/字**（线性，无截断）。

> 注：D6 commit 记录的是「+37ms/字」，本次复测得 ~79ms/字。差异来自文本集范围
> （D6 最长 20 字，本次到 52 字）与机器负载。**以本次为准**，两者量级结论一致。

⇒ 首句 20 字压到 12 字，理论省 ~600ms。与换引擎同量级。
但代价：要**让 LLM 说更短的话**，且 `SentenceSplitter` 已决策「不在逗号处切——
半句送 TTS 语调会塌」。属产品取舍。

**杠杆 B：换更快的引擎**

已排除：
- 线程数：melo 1/2/4/8 线程实测 → **4 线程最优**（812ms），1 线程 906ms、8 线程 918ms，已是最优
- 重采样：44.1k→24k 只占 **0.13ms**，不是瓶颈
- 增量流：两引擎都只回调 1 次，不支持

## 五、本次发现的问题

### 5.1 Chunker 从不 flush，句尾音频被丢弃 —— ✅ 已修（2026-09-23）

`serial.py:87` 与 `pipelined.py` 都只调 `chunker.feed()`，**从不调 `chunker.flush()`**。

后果：
- 每句尾部不足 200ms（9600 字节）的音频永久留在 buffer，**被静默丢弃**
- 若首句音频 < 200ms，`first_audio_out` 永远打不上 → 该轮口径B 记为 -1（缺失）

实测（`Chunker` 单元行为）：输入 20000B → feed 出 2 片（19200B），**800B 滞留在 buffer**。

#### 修法与实测（a2fb156 之后，2026-09-23）

新增 `Chunker.feed_and_flush(data)` = `feed() + flush()`，三个调用点（serial `_synthesize`、
pipelined 投机 `_synth_into`、pipelined 兜底 `_emit`）改为一句合成完**立刻补齐尾部**，
而不是把残余留给下一句——这样首句不足 200ms 时 `first_audio_out` 也能在当拍打上。

真 WS 链路复核（`--tts melo --gating neural --repeat 3`）：

| | 修前（09-22） | 修后（09-23） |
|---|---|---|
| audio_bytes / 轮 | 28800 / 48000 / 86400（全是 9600 整数倍） | **35438 / 76134 / 82606**（尾片回来了） |
| 口径B p50 | 1756~1814ms（句1） | 1531~1634ms（句1，同一量级，属 LLM 抖动） |

结论：**丢音修好了，延迟没变**（尾片与最后一片整片同时到达，不额外占时间）。
回归测试：`test_short_sentence_tail_is_not_dropped`（8k/200ms TTS 造 3200B/句，
修复前这一轮 0 个音频片、口径B = -1，已反向自测确认按预期报红）。

### 5.2 上行测试语音必须用 kokoro

`bench_ws.py:91` 已记录：**melo 合成的语音喂给 ASR 识别结果为空**。
本次用 melo 生成上行语音复现了这个坑（`final` 得到 `'一下'`、`'发'` 等碎片）。
含义：melo 只能做下行 TTS，不能用来造测试语音。

## 七、一句话结论

**流程已经没有并行空间可挖了**：能并行的都并行了，投机被 ASR 尾部延迟原理性锁死，
TTS 没有增量流。剩下的唯一真实杠杆是**首句字数**（~79ms/字），
但它要求 LLM 说更短的话——这是产品取舍，不是技术优化。

300ms 在当前架构下差 5 倍，不是差一点。
